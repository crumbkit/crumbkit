# ADR-0030. Trace context

- A run joins the trace of whatever started it through W3C Trace Context Level 1, a W3C Recommendation (https://www.w3.org/TR/trace-context/), and keeps the random-trace-id flag of Level 2 (https://www.w3.org/TR/trace-context-2/). The context travels in the `TRACEPARENT` and `TRACESTATE` environment variables of OpenTelemetry's environment-variable carrier, which is a Release Candidate in specification v1.61.0 (https://github.com/open-telemetry/opentelemetry-specification/blob/v1.61.0/specification/context/env-carriers.md). crumbkit reads only those two uppercase names, reads them once at start-up, and injects the context into the environment of a child.
- With the `usage-log` feature, `crumbkit::usage::start` reads both variables through one strict parser, and ignores the `traceparent` that is-ai-agent reports. The parser accepts two lowercase hex digits of version, a trace id of 32, a parent id of 16 and flags of 2, joined by single dashes. Version `ff`, uppercase hex, an all-zero trace id and an all-zero parent id are invalid, a version `00` value has exactly 55 characters, and a higher version is read for its first four fields when a dash or the end follows the flags.
- A valid `TRACEPARENT` gives the run the caller's trace id, the caller's span id as its parent, and the caller's `TRACESTATE`. A missing or invalid `TRACEPARENT` starts a new trace with a random id and no parent, and the run discards the caller's `TRACESTATE`, as W3C requires.
- Each run has a trace id of 16 bytes, its own run id of 8 bytes, which is the span id its children name as their parent, and the parent id when the caller's `TRACEPARENT` was valid. `start` reads the random bytes of a new trace id and the run id from `/dev/urandom`, through the same reader as the usage log's key. A failed read or an all-zero id means the run installs no recorder, so it writes no line and gives its children no variables.
- The `crumbkit/usage/v1` record holds `trace` as 32 lowercase hex digits, `run` as 16, and `parent` as 16, which is left out for a new trace (ADR-0029). The trace ids are random values that the caller already shares with its other children, so the record holds them unhashed, and the keyed `session` hash still groups an agent's runs.
- A tool passes the trace to a child with `Command::envs(crumbkit::trace::child_env())`. `child_env` exists in every build, and returns variables only when the usage log started and the run reached `parse`, because only such a run writes a line. Otherwise it returns none, so the child inherits the caller's variables unchanged and never names a parent span that nothing records.
- `child_env` returns `TRACEPARENT` as `00-<trace>-<run>-<flags>`, whatever version the caller sent. The flags keep the caller's sampled bit (`01`) and random-trace-id bit (`02`) and clear the other bits, as Level 1 requires for bits it does not define, and a new trace has the flags `03`. Every child of one run gets the same variables, so children that run one after another or in parallel all name the run as their parent.
- `child_env` returns the caller's `TRACESTATE` unchanged when the caller's `TRACEPARENT` was valid. When the run started a new trace and the caller set `TRACESTATE`, `child_env` returns `TRACESTATE` with an empty value, which the child's environment holds in place of the caller's value, and a `TRACESTATE` that is not UTF-8 counts as empty. W3C Trace Context Level 1 section 3.3.1.1 says vendors "MUST accept empty tracestate headers", and OpenTelemetry's propagator requirements in v1.61.0 treat an empty trace state as no state, so a child never sees the state of another trace.
- When the caller set no `TRACESTATE`, `child_env` returns no `TRACESTATE`. crumbkit never reads, forwards or records `BAGGAGE`, so a child inherits it as it would without crumbkit.
- The `tracing` cargo feature, off by default, runs `parse` and `finish` inside the spans `crumbkit.parse` and `crumbkit.finish` of the `tracing` crate, at level `INFO` with the target `crumbkit`. crumbkit installs no subscriber, and a tool that wants one span per run opens its own span in `main`, because crumbkit cannot wrap the handler that runs between `parse` and `finish`.
- The spans' fields follow OpenTelemetry's semantic conventions for CLI programs, v1.44.0 with Development status (https://github.com/open-telemetry/semantic-conventions/blob/v1.44.0/docs/cli/cli-spans.md), where one exists: `process.exit.code`, and `error.type` for the failure code in the tool's spelling. `crumbkit.command` holds the command path, and with a started usage log the spans also hold `trace_id` and `crumbkit.run`. The trace id field is `trace_id` because that is the name OpenTelemetry gives the trace id in log formats other than OTLP.
- The feature works without the usage log, and its spans then have no ids. When the subscriber disables crumbkit's spans, crumbkit records nothing on the tool's own span.
- Nothing that crumbkit records holds a value the caller typed. Only hex that the parser validated reaches the record, no span holds an argument's value, the command line, `process.command_args` or `TRACESTATE`, and shelf's end-to-end test plants a secret in `TRACEPARENT` and `TRACESTATE` and fails when the log holds it.
- crumbkit does not provide per-request runs for a long-running server, and it does not export spans over OTLP.

Considered: a crumbkit-specific run-id variable, a free-text correlation id, always giving children this run's id, forwarding `BAGGAGE`, a crumbkit timing API, crumbkit installing a subscriber, hashing the trace ids, omitting `TRACESTATE` for a new trace, `trace.id` as the span field.
