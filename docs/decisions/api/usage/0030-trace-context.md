# ADR-0030. Trace context

- A run joins the trace of whatever started it through W3C Trace Context Level 1, a W3C Recommendation (https://www.w3.org/TR/trace-context/), and keeps the random-trace-id flag of Level 2 (https://www.w3.org/TR/trace-context-2/). The context travels in the `TRACEPARENT` and `TRACESTATE` environment variables of OpenTelemetry's environment-variable carrier, which is a Release Candidate in specification v1.61.0 (https://github.com/open-telemetry/opentelemetry-specification/blob/v1.61.0/specification/context/env-carriers.md). crumbkit reads only those two uppercase names, reads them once at start-up, and injects the context into the environment of a child.
- With the `usage-log` feature, `start` reads `TRACEPARENT` through one strict parser and ignores the `traceparent` that is-ai-agent reports, so only hex that the parser validated reaches the record. A missing or invalid `TRACEPARENT` starts a new trace, and the run then discards the caller's `TRACESTATE`, as W3C requires.
- Each run has its own run id, which is the span id its children name as their parent. A run that cannot read random bytes installs no recorder, so it writes no line and gives its children no variables.
- The usage record holds the trace ids unhashed, because they are random values that the caller already shares with its other children, and the keyed `session` hash still groups an agent's runs (ADR-0029).
- A tool passes the trace to a child with [`trace::child_env`](../../../../crates/crumbkit/src/trace.rs). It asks the run observer for them, so it returns variables only when the usage log is the observer and the run writes a line, and a child never names a parent span that nothing records (ADR-0057).
- `child_env` passes on only the flag bits that Level 1 and Level 2 define, as Level 1 requires for bits it does not define. Every child of one run gets the same variables, so children that run one after another or in parallel all name the run as their parent.
- When the run started a new trace and the caller set `TRACESTATE`, `child_env` returns an empty `TRACESTATE`, which replaces the caller's value in the child's environment. W3C Trace Context Level 1 section 3.3.1.1 says vendors "MUST accept empty tracestate headers", and OpenTelemetry's propagator requirements in v1.61.0 treat an empty trace state as no state, so a child never sees the state of another trace.
- crumbkit never reads, forwards or records `BAGGAGE`, so a child inherits it as it would without crumbkit.
- The `tracing` cargo feature, off by default, runs `parse` and `finish` inside spans of the `tracing` crate ([`trace`](../../../../crates/crumbkit/src/trace.rs)). The spans record the trace id and run id that the run observer gives. crumbkit installs no subscriber, and a tool that wants one span per run opens its own span in `main`, because crumbkit cannot wrap the handler that runs between `parse` and `finish`.
- The spans' fields follow OpenTelemetry's semantic conventions for CLI programs, v1.44.0 with Development status (https://github.com/open-telemetry/semantic-conventions/blob/v1.44.0/docs/cli/cli-spans.md), where one exists. The trace id field is `trace_id`, because that is the name OpenTelemetry gives the trace id in log formats other than OTLP.
- Nothing that crumbkit records holds a value the caller typed. No span holds an argument's value, the command line or `TRACESTATE`, and shelf's end-to-end test plants a secret in `TRACEPARENT` and `TRACESTATE` and fails when the log holds it.
- crumbkit does not provide per-request runs for a long-running server, and it does not export spans over OTLP.

Considered: a crumbkit-specific run-id variable, a free-text correlation id, always giving children this run's id, forwarding `BAGGAGE`, a crumbkit timing API, crumbkit installing a subscriber, hashing the trace ids, omitting `TRACESTATE` for a new trace, `trace.id` as the span field.
