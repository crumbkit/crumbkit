# ADR-0029. Usage log

- The usage log appends one JSON line per run of a tool to a file on the user's machine. The line records the shape of the run, such as the command path, the flags typed and the exit code, and never the values that the caller typed. A later reader of the log shows where callers waste effort, such as refused flags, help requests before a command and listings that were cut short.
- The log sits behind crumbkit's `usage-log` cargo feature, which is off by default, so a tool without the feature compiles none of its code and none of its dependencies (ADR-0003). The feature adds siphasher for the hashes, etcetera for the state directory, is-ai-agent to name the caller, humantime for the time and signal-hook for the signal thread. It builds only on Unix, because the key comes from `/dev/urandom`, the session falls back to the parent process id and the files get Unix modes.
- A tool turns the feature on and adds one line to `main`: `let _log = crumbkit::usage::start();`. `start` takes no arguments. It notes the start time, installs one recorder for the whole process in a static `Mutex` and starts the signal thread, and returns a `#[must_use]` guard that writes the line when it drops, after `main` has flushed the tool's output. A second `start` in the same process returns a guard that does nothing.
- `parse` gives the recorder the tool's name and version from the command it parses against, as it reports the rest of the run, so `start` never builds the command tree. A run that ends before it reaches `parse` writes no line, because the line has no tool name to go under.
- `parse`, `parse_from` and `parse_to` report the command path, the long name of each flag the caller typed, read from clap's value source and including global flags, and the short name such as `-q` for a flag without a long one. They report a request for help as `short` for `-h` and `long` for `--help` or the `help` command, with the command path that the help names. For a refused command line they report how many flags name no flag of the command, clap's suggested real flag, exit code 2 and the code `crumbkit::cli::usage` in the tool's spelling. For a parsed command line they report how many values the command's positional arguments with the value name `ID` received.
- `finish` and `finish_to` report the exit code, the code of a failure or refusal in the tool's spelling, the bytes written to standard output and whether a listing showed fewer rows than its total. A batch reports the code of its first failure.
- crumbkit-aliases' `expand` calls `crumbkit::usage::aliased()` when it replaces an alias, and the line records `"alias": true` and the expanded command. `aliased` exists in every build and does nothing without the feature or a started log, so crumbkit-aliases has no feature of its own.
- Every report does nothing when no recorder is installed. A report is a lock of the static `Mutex` and a check of its state, and only `parse` copies the words of the command line, once.
- The line is the `crumbkit/usage/v1` record, whose schema is checked in as `crates/crumbkit/schemas/usage-v1.json` (ADR-0007). It has `schema`, `tool`, `version`, `at` in RFC 3339 with milliseconds, `command`, `help`, `flags`, `ids`, `unknown_flags`, `nearest`, `alias`, `exit`, `code`, `ms`, `out_bytes`, `truncated`, `caller`, `session`, `args`, `trace`, `run`, `parent`, `interrupted` and `ext`. `trace`, `run` and `parent` place the run in a W3C trace (ADR-0030). A field that does not apply to the run is left out.
- The record holds no argument values, URLs, ids, paths, error text or messages. Inside crumbkit, its types enforce this. Every name in the record is a `Name`, whose only constructors take a `clap::Command` for its name, its version or a path of its subcommands, a `clap::Arg` for its long or short flag name, or a crumbkit `Code` in the tool's `Spelling`, so no crumbkit code can put a word that the caller typed into a name. The counts are numbers, the trace ids are hex that crumbkit generated or validated, and the command line appears only as a keyed hash. The types do not check the text that the tool itself gives its commands, arguments, version and codes, or the tool's `ext` section. shelf's end-to-end test plants `s3cr3t-<field>-PLANTED` in option values, positionals, a command path, an unknown flag's name and its value, a help topic, an unknown command, `TRACEPARENT` and `TRACESTATE`, and fails when any line of the log holds `PLANTED`.
- `caller` is the id that is-ai-agent gives for the coding agent that ran the tool, such as `claude-code`. Without an agent, it is `person` when standard input is a terminal and `unknown` otherwise. `session` is the keyed hash of the agent's session id, or of the parent process id when the agent gives none, so the runs of one session or one shell share a value.
- `session` and `args` are keyed SipHash-2-4 hashes, written as 16 lowercase hex digits. `args` hashes every word after the tool's name, each with its length, so identical command lines share a hash and different ones almost never do. SipHash-2-4 is a keyed pseudorandom function built for short inputs, so without the key nobody can test a guessed command line against a hash, and it needs no further crate. The key is 16 random bytes from `/dev/urandom`, kept in `usage.key` beside the log with mode 0600. The first run writes the key to a temporary file in the same directory, syncs it, and links it into place as `usage.key` with `hard_link`, which fails when the name exists, so `usage.key` either holds 16 bytes or does not exist, and when two first runs race, the loser reads the winner's key. A `usage.key` that does not hold 16 bytes, such as one left by an older version, is replaced with a new key through `rename`, so the run and later runs write their lines again.
- The log is `<state dir>/<tool>/usage.jsonl`, where the state directory is `$XDG_STATE_HOME`, or `~/.local/state` when that variable is unset, empty or relative, as etcetera gives it. crumbkit creates the directory with mode 0700 and the file with mode 0600.
- A run appends its line while it holds the file's lock, which it takes with `File::try_lock`, retrying for at most 100 ms before it drops the line. A line longer than 1 KiB is dropped. When the file is over 10 MB, the run keeps its newest whole lines that fit in 5 MB and then appends its own, while it holds the lock, so at least 5 MB of new lines go in before the next trim. A last line without a newline is a write that ended early: a trim drops it, and the next append starts on a new line, so the torn line never joins the next record.
- The signal thread waits for SIGINT and SIGTERM. On a signal, the thread writes the line with `"interrupted": true` and then lets the signal take its default effect, so the process ends as it would have without the log. When the main thread is already writing the line, the signal thread waits for that write to finish, for at most 500 ms, before the signal takes effect, so the signal never cuts the line in half. The bound covers the 100 ms lock wait and a trim on a disk that reads and writes about 40 MB a second. A process that started with one of the two signals ignored now ends on it, such as a background job of a non-interactive shell, which starts with SIGINT ignored. A tool that handles one of the two itself ends on it too. Both follow from crumbkit's ban on unsafe code, which rules out the `sigaction` call that reads a signal's disposition. SIGHUP is left alone, so a run under `nohup` behaves as it would without the log.
- Each run writes at most one line. Recording never changes the tool's output or exit code: every failure to write is silent, and a poisoned lock counts as no recorder.
- A tool adds its own fields with `crumbkit::usage::section(document, &value)`, which sets `ext` to `{"schema": <document id>, "data": <value>}`. The tool owns the section and keeps values out of it, because crumbkit cannot check it, and the section counts towards the 1 KiB limit.

Considered: a key file created with `create_new` and then written, HMAC-SHA256 with a key from getrandom, a log handle passed to `parse` and `finish`, a `start` that takes the tool's command, a signal thread that also waits for SIGHUP, counting every positional value as ids, a session from the agent's id only, a log that ships off the machine, a record per refused flag.
