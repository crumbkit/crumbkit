# ADR-0015. Lightweight adoption

- crumbkit is light to adopt in concepts and in dependencies. A tool keeps its own clap derive types and its own `main`, and each part works on its own, so a tool adopts only the parts it wants. The default build depends only on clap, serde, serde_json and schemars.
- Each part follows an existing convention: `Failure` extends `std::error::Error`, `Output` is added with clap's `#[command(flatten)]`, results derive `Serialize` and `JsonSchema` and implement `Row` to name their table columns, and each crumbkit-test check is a free function that a tool calls from an ordinary `#[test]`, as it calls clap's `Command::debug_assert`.
- The optional `crumbkit::run` one-liner is a thin layer over the public parts. It adds no concept, does nothing a hand-wired `main` cannot, and no part requires it.
- Help pages, the `Call`s in `Next:` lines and recoveries, and MCP tool lists are rendered from the `clap::Command` a tool builds at runtime, which may hide or remove commands. A tool's `main` passes that `Command` to `Output::set_command` once after parsing, and `finish` renders each `Call` against it. A `Next:` line whose `Call` names a missing or hidden command or argument is left out, and so is every `Next:` line when no command is set. A recovery's `Call` in those cases prints as `Recovery::None` with crumbkit's reason (ADR-0001).
- A command sets its own output defaults on its arguments type, such as the default limit of the `Page` it flattens. An optional table passed to `crumbkit::parse` sets defaults for a branch by command path, and the nearest entry wins, written into each flag's default before parsing.
- A command that refuses the caller returns an ordinary `Failure`. crumbkit-test and the golden files check the full tree.
- crumbkit-test checks a command tree with four free functions, each of which takes a `clap::Command` and its settings as plain arguments: `check_names(command, exempt)`, `check_grammar(command, verbs, exempt)`, `check_listings(command, exempt)` and `check_filters(command, exempt)`. Each collects every problem it finds and panics, as a failed assertion does, with one problem per line that names the command by its path from the command passed in, such as `shelf books list`. A bundled `check(Cli::command())` that runs every check waits until the help-tree checks exist.
- `check_names` fails on every alias of a command or an argument, visible or hidden, so a retired name fails to parse; an argument may have one short form beside its long name. `check_grammar` requires the form `<tool> <resource> <verb>`: a command without subcommands is `list`, `show` or a verb the tool passes, and a command with subcommands is a resource, which may nest and is named in lowercase letters and digits in words joined by single dashes. It also fails on an argument named `--dry-run`, because that name is reserved for the write verbs that come after 0.1. It checks only a name's form, so review checks that each resource is plural.
- `check_listings` requires a `--limit` that takes a value and an `--all` flag, as flattening `Page` gives them, on every `list` command, and a required positional argument that takes from 1 to 100 values and accepts more than one on every `show` command. `check_filters` requires every option that accepts many values to accept both repeats and commas, through `ArgAction::Append` and the value delimiter `,`.
- Each tree check takes a list of exemptions, each the path of a command below the command passed in, such as `"books list"`, and skips that command and everything below it for that check only. An exemption that names no command fails the check, so the exemption of a removed command cannot stay. The checks walk the tree as the tool built it, without `Command::build`, so they never see clap's generated `help` subcommand or its `--help` and `--version` flags, and they check a global argument once, on the command that defines it.
- Every function that takes a `clap::Command` works on any node of the tree, so a crate or a team can apply crumbkit and crumbkit-test to its own subtree. The `schema` and `self usage` commands and the usage log stay at the root.
- The first segment of a code names the component that owns the code, so a crate keeps its codes in whatever binary includes it. In a tool built from one crate, the component and the tool have the same name.
- `show` accepts many ids and returns a `Batch` (ADR-0016). `crumbkit::fetch_each(ids, workers, lookup)` runs a per-id lookup on a bounded number of scoped threads and returns one result per id, in the order given. A tool whose backend has a batch lookup calls that lookup directly instead.
- With one worker, one id or none, `fetch_each` runs every lookup in the calling thread and starts no thread, and crumbkit has no default worker count, so each tool chooses one. An async tool uses its own bounded stream, because `fetch_each` blocks the calling thread, and a tool that needs rate limits or retries writes its own loop.

Considered: an `App` runner that owns dispatch, a required derive macro, rendering from the compile-time tree, a trait with a provided `show_many`, an async runtime for concurrent lookups, a default worker count for `fetch_each`, builder-style tree checks, one grammar check with per-rule exemptions, a bundled tree check now, no short flags, only `-h` and `-V` as short flags, a fixed verb list with exemptions, a plural check.
