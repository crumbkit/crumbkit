# ADR-0016. Result formats

- Results come in two formats: compact text for people and agents, and JSON for programs. The text table already has a header row, one record per line and no repeated keys.
- Markdown is used only to export help, through `schema cli --markdown`.
- A type that prints as a table row implements `Row`. Its `COLUMNS` are the compact columns in display order, its `LONG_COLUMNS` are the columns that `--long` adds after them, and both hold serialized field names. A field in neither list appears only with `--json --full`.
- `finish` takes one `Row`, a `Vec` of rows or a `Listing` through the sealed `Rows` trait. A single row's JSON `data` is an object, and a `Vec`'s or a `Listing`'s is an array.
- The text table has a header row with each column name in upper case, then one line per row, and an empty result prints the header only. Each column is as wide as its widest cell in characters, two spaces separate the columns, and the last column is not padded, so no line ends in spaces.
- A cell shows a string as it is, a number or boolean in its JSON form, `null` or a missing field as `-`, and an array or object as compact JSON. A control character in a string shows in its `char::escape_default` form, such as `\n` or `\u{1b}`, so each row stays on one line.
- A tool adds the `Output` flags with `#[command(flatten)]`, and they are global. `--json` prints the document on one line, `--long` adds the long columns in text and JSON, and `--full` requires `--json` and prints every field in declaration order. `--fields a,b` prints exactly the named fields in that order, conflicts with `--long` and `--full`, and exits with code 2 on a name that is not a property of the row type's JSON Schema.
- A command that may show fewer rows than matched flattens `Page` into its own arguments, which gives it `--limit <N>` and `--all`; the flags belong to that command and are not global. The default limit is `Page`'s const parameter, 25 unless the command names another such as `Page<4>`, so the command's `--help` shows it; `--limit` parses as a `NonZeroUsize`, so clap refuses 0, and clap refuses `--all` with `--limit`. crumbkit implements `Serialize` and `JsonSchema` for `Page` by hand, so its normal dependencies need no `serde_derive` or schemars `derive`.
- Such a command returns a `Listing`: one page of rows, the number of rows that matched, and an optional description such as `books`. `Listing::new` takes a page and a total that the tool counted itself, so a handler never loads a row it will not print, and it raises a total smaller than the page to the number of rows. `Listing::from_all` truncates rows that are already in memory and counts them all.
- When a listing shows fewer rows than its total, a footer line follows the table on standard output with no blank line before it: `Showing {shown} of {total} {description}. --all shows every one.`, or the same line without the description when the listing has none. The footer also follows the table with `--long` and `--fields`. crumbkit owns the wording, the tool supplies only the description, and the numbers print without separators.
- A listing may carry one next step, a `Call` and a phrase from the tool. In text output only, the line `Next: {call} {phrase}` follows the table and any footer on standard output with no blank line before it, such as `Next: shelf books show <ID>... takes up to 100 ids in one call.`, and it also appears with `--long` and `--fields`. `finish` leaves the line out and still exits 0 when no command is set or the call does not resolve in that command, and the JSON document never holds the step.
- `finish` takes the handler's `Result`. An `Err` prints the failure as text on standard error with nothing on standard output, or with `--json` as one `crumbkit/failure/v1` document on standard output followed by a newline, and exits with code 1. `--long`, `--full` and `--fields` leave a failure unchanged, and a `--fields` name that the row type lacks still exits with code 2 before anything prints.
- The text form of a failure is an `error:` line holding the failure's `Display`, a `cause:` line for each error in its source chain, a `help:` line, a `code:` line, and a `url:` line when the failure has a url. The labels are indented by two spaces and the values line up. `help:` reads ``run `<call>` `` for `Run`, `run the same command again later` for `Retry`, the text for `Hint`, and `no next step: <reason>` for `None`, and a control character in any value prints in its `char::escape_default` form.
- `finish` writes through a `Sink`, which owns standard output and standard error, and `finish_to` writes into a given sink, so tests run in memory. A pipe that the reader closed early exits with code 0 after a result and code 1 after a failure, and any other write error exits with code 1.

Considered: a failure on standard output without `--json`, TOON, a Markdown result format, unicode-width for cell widths, serde_json's `preserve_order` feature for column order, global paging flags, the footer on standard error, the description in the JSON document, deriving `Serialize` and `JsonSchema` for `Page`.
