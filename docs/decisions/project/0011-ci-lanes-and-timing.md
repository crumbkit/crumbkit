# ADR-0011. CI lanes

- Pull requests run a fast lane whose median wall time stays within the limit of CI-3. The fast lane has two work jobs, `lint` and `test`, which run in parallel on `ubuntu-latest`, because GitHub's standard runners are free for a public repository and `ubuntu-latest` has 4 CPUs, so cargo compiles the workspace's crates and runs its tests in parallel, which the single CPU of `ubuntu-slim` cannot. `lint` runs rustfmt, clippy, the MSRV check that RUST-9 gives, `cargo xtask check`, rustdoc with warnings denied (DOCS-4), cargo-deny, cargo-shear and zizmor, and `test` runs the tests. Every extra job repeats the checkout, the toolchain installation and the cache restore, so a third work job would shorten a run only by the steps it took from the longer job.
- `ci.yml` also runs `lint` and `test` on each push to `main`, so the merged code is tested even when `main` moved after a pull request's last run. This costs one extra run of the pull-request jobs per merge. A newer push to `main` cancels the run of an older one, and the repository has no merge queue, so `ci.yml` has no `merge_group` trigger.
- The `gate` job needs every fast-lane job, runs even when one of them failed or was cancelled, and fails unless all of them succeeded. The repository ruleset can then require `gate` alone, and a job that joins the fast lane needs no change to the ruleset. `gate` runs on `ubuntu-slim`, because it only reads the results of the other jobs.
- The repository ruleset `main` requires the `gate` check from GitHub Actions to pass before a pull request merges, requires every change to `main` to come through a pull request, and blocks force pushes to `main` and its deletion. It does not require a branch to be up to date with `main`, because the run on each push to `main` tests the merged code, and requiring it would add one more run of the fast lane to every pull request that merges after another. It requires no approving review, because the owner cannot approve their own pull requests.
- `test` runs the tests with cargo-nextest, whose `ci` profile reports every failing test in one run, and runs the doctests with `cargo test --doc`, because nextest does not run doctests.
- shelf turns on crumbkit's `miette`, `usage-log` and `tracing` features, so the workspace runs build, test and lint crumbkit with all three. `test` runs crumbkit's tests and doctests again on their own in the default build and with `miette`, and `lint` runs clippy on crumbkit in the same two builds and with `tracing` alone, which is the only build that compiles the spans without the usage log's ids. A separate `usage-log` run would repeat what the workspace runs already check. Each is one more step in an existing job, because a new job repeats the setup time. Clippy runs once per build, because a single `--all-features` run misses a warning that only one build shows.
- The `scheduled.yml` workflow runs a nightly slow lane on `ubuntu-latest`. It runs `cargo deny check advisories` and `cargo xtask ci-time`, which fails when the median of the last 20 successful pull-request runs is over the limit of CI-3. The nightly job has no rust-cache, because it compiles little. Fuzzing and benchmarks join the nightly lane once code for them exists.
- `ci.yml` runs the tests on `macos-latest` on each push to `main`, and leaves them out of pull requests and the gate, because GitHub runs only a few macOS jobs of an account at once, so a pull request would wait for a free macOS runner. A failure there shows on the commit on `main`.
- The `lint`, `test` and `macos` jobs use rust-cache, and only a run on `main` saves a cache. A pull request restores the cache that `main` saved, because GitHub lets a pull request restore the caches of its base branch. Pull requests therefore skip the time of saving and leave the repository's cache storage to `main`, and GitHub evicts the oldest caches when that storage is full.
- When the nightly job fails, the `report` job comments the run's URL on the open issue titled "Scheduled CI failed", or opens that issue when none is open, so every failure stays on one issue.
- Every Rust job runs on a GitHub image that includes rustup, and `rustup toolchain install` installs the toolchain that `rust-toolchain.toml` pins.
- Workflows start with `permissions: {}` and pin actions to commit SHAs, and zizmor lints the workflows and the Dependabot configuration in the `lint` job.

Considered: two jobs on the single-CPU `ubuntu-slim` runner, one sequential job, a ruleset that requires branches to be up to date, no run on pushes to `main`, one job per check, a separate job for each crumbkit feature, a separate MSRV job, nextest partitions across jobs, the arm64 `ubuntu-24.04-arm` runner, larger runners, `cargo test` for every test, sccache, code coverage, macOS tests on every pull request, weekly or nightly macOS tests, a rust-cache key shared by all jobs, rust-cache saves from pull requests, one issue per failed run.
