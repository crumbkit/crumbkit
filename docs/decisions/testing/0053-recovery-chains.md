# ADR-0053. Recovery chains

- crumbkit-test's [`check_recoveries`](../../../crates/crumbkit-test/src/recoveries.rs) runs command lines that fail, which the tool's test lists with the code each fails with, and follows each `run` recovery and alternative that the failures print, up to 3 steps by default. A run that prints several failures, such as a batch, starts one branch for each, and a start passes when any of its failures carries its code, because a batch reports every id that failed. A step that the parser refuses fails the check, and so does a step that fails with the code of the failure it follows or of any earlier failure of its chain, because an agent that follows the recovery would meet a failure that it has already seen. An opt-out from `Rule::SameCode` names the command that such a step runs, which marks a step that a person or an agent must complete by hand first. A failure with one of the tool's declared codes that offers no `run`, `retry` or `hint` step fails the check, at the start and after any step, because an agent that reads it has nothing to act on. A `none` step with a reason counts as no next step, and an opt-out from `Rule::NextStep` that names the failing command declares the exception that ADR-0001 allows. A failure from a run that writes crumbkit's warning about a recovery that does not render is not reported again as a dead end. Every declared code is provoked by a chain or listed with the reason no test can provoke it. The check pins the chains, codes and outcomes in the golden file `recoveries.txt`, without messages, so a changed recovery shows in review.
- The runs of one chain share fresh XDG directories, so a step sees what the earlier runs wrote, such as a confirmation that a remove needs. `Failing::env` sets or removes environment variables for every run of the chain, for a failure that the environment provokes. Its entries win over `Examples::env` and the fresh XDG directories, and the report names the start with them, such as `tool books list (with DEPTH=1)`. A placeholder such as `<ID>...` or `<path>` takes the first value of three sources: the chain's own `Failing::values`, then a field of the failure that offers the step, then the shared `Recoveries::values`, so each chain can fill `<path>` with the path its own failure named. Each placeholder that a field fills is a finding of `Rule::FieldValue`, id `recoveries/field-value`, and the report shows it under the step, because an agent that follows the recovery must copy the value itself, while a recovery built with `Call::value` carries it. A tool that cannot carry the value opts out with an `Allow` that names the command whose failure printed the recovery. A start's own value that wins over a field is no finding. A step that runs with every value of a list field, such as the `all` step of a batch's over-budget failure (ADR-0046), runs once with every value of the field, each as its own word, in place of the first word that is one placeholder, such as `<ID>...`. That fill is no finding, because the step itself names the field its values come from. A field that is missing or holds no value fails the check. When the run with every value fails again with the same code and its failure's field holds fewer values than the run was given, the step is no `Rule::SameCode` finding, because the run answered some keys and the chain makes progress. A run that leaves as many values as it was given is a finding, because the agent learns nothing new. A table value matches the name exactly, case included, because a tool may write its placeholders in either case. A field matches with capitals lowered and `-` read as `_`, because field names are always lowercase and clap writes its placeholders in capitals. A null, list or object field fills no placeholder, because an agent cannot pass JSON as one word of a command line, so the next source fills it or the check reports the placeholder without a value. The fields come with the failure that the check reads: those that the tool's form or reader returns in its `ReadFailure`, or the `fields` of crumbkit's failure document, so the code, steps and fields always belong to one failure. A placeholder can sit anywhere in a word, so `<plugin>.<capability>` fills two placeholders and keeps the `.`, and a `<` that starts no placeholder stays literal text. The check reads a step's words with its own `split`, which reads single and double quotes as a POSIX shell does and refuses a `$` or a backtick between double quotes, so a tool need not re-quote its hints with `help::quote`. `split` is private to crumbkit-test, because only the check reads a recovery's words, and crumbkit offers only `help::quote`. A code that the tool does not declare and crumbkit does not own ends its chain, and the report counts such codes.
- `check_recoveries` runs each start and step in the working directory, standard input and XDG fixture that ADR-0005 describes for examples and twins.

Considered: a field fill reported only in the golden file, an opt-out that names the step's command, a finding for a `Failing::values` entry that wins over a field, setup command lines that run before a start, a setup function that receives the XDG paths, shared values that win over a failure's fields, fields that match a placeholder's case exactly, a second read of the document's fields beside the failure, placeholders joined only by fixed separators, following recoveries from the failures that the examples provoke, generating failing command lines from the clap tree, a recovery check without a golden report, variables of a start that apply only to the start and not to its steps, a list or object field that fills a placeholder with its JSON text, a list field that fills a repeated placeholder such as `<ID>...` with one word for each item, an `each` step run once for every value of its field, a run with every value that fails with the same code counted as a finding even when it leaves fewer values.
