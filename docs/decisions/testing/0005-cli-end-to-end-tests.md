# ADR-0005. End-to-end tests

- End-to-end tests run the built binary through snapbox's `cmd` module with a cleared environment and temporary XDG directories.
- crumbkit-test's [`check_examples`](../../../crates/crumbkit-test/src/examples.rs) runs every example of every leaf in the tool's guide against the tool's built binary, so each command line that help shows is a run that works.
- cargo gives the binary's path only to the integration tests of the binary's own package, so the check runs from one. An integration test imports only from a library, so that package has a library target that exports the clap command and the guide, and its binary calls the library, as shelf's does.
- The check runs each example with no shell, a cleared environment and fresh XDG directories, so a run depends only on what the example and the check give it. It runs the examples of hidden commands, because their own help lists them.
- The golden file holds the run's standard output only. A run that exits with a code other than 0 or writes to standard error fails the check, because an example shows a run that works.
- The check fails on a stale golden file, so the directory holds only example golden files, and on an opt-out from running a command's examples that names no command or skips no example, as the other tree checks do (ADR-0036).
- crumbkit-test's [`check_recoveries`](../../../crates/crumbkit-test/src/recoveries.rs) runs command lines that fail, which the tool's test lists with the code each fails with, and follows each `run` recovery and alternative that the failures print, up to 3 steps by default. A step that the parser refuses or that fails again with the same code fails the check, because an agent that follows the recovery would be stuck. Every declared code is provoked by a chain or listed with the reason no test can provoke it. The check pins the chains, codes and outcomes in the golden file `recoveries.txt`, without messages, so a changed recovery shows in review.
- The runs of one chain share fresh XDG directories, so a step sees what the earlier runs wrote, such as a confirmation that a remove needs. A placeholder such as `<ID>...` takes a value that the test gives by name. A code that the tool does not declare and crumbkit does not own ends its chain, and the report counts such codes.
- A test of a refusal runs a twin with [`check_twin`](../../../crates/crumbkit-test/src/twins.rs): a command line that differs from the refused one by one word and succeeds. The twin shows that the changed word is the reason for the refusal, so the test cannot pass because the command fails for another reason (TEST-1).

Considered: trycmd, assert_cmd, running the examples through a shell, golden files that also hold standard error and the exit code, the inherited environment for example runs, finding the binary from a unit test, including the tool's source files in the test with `#[path]`, following recoveries from the failures that the examples provoke, generating failing command lines from the clap tree, a recovery check without a golden report, twins that differ by any number of words.
